# Rebuild validation gates

This is an acceptance plan, not evidence that any milestone has passed. A link or a matching function does not prove a playable program. The existing reference matching and official checks remain independent, unchanged gates. Run comparison tools that check out or clean files only in disposable scratch worktrees. The initial compile budget is at most two simultaneous compiler jobs; coordinate full builds with the toolchain owner.

## Evidence and isolation

For every run record the source revision and dirty state, recipe digest, exact command and exit status, tool and compiler identities/versions, configuration, start/end time, counts, and the paths to private evidence. Record skipped, failed, unknown and unsupported cases explicitly. Keep sensitive inputs outside the repository. Generated outputs, logs and inventories may use the ignored build/rebuild/ directory or a private directory outside the checkout; never publish binaries, assets, object files, game bytes, disassembly, credentials or personal paths. Review even metadata before sharing. Preserve the existing oracle and `build/units.json`; a runtime selection never replaces reference variants. Use owned compatible inputs as described by the README. No copy-protection bypass is part of validation.

Use a dedicated private test profile, save directory, and artifact directory, isolated from ordinary game saves and other runs. Verify the actual save path before creating or loading a save; retain a manifest of the test files and hashes in private evidence. Do not touch the user's existing saves. Capture observations and failure logs privately, with enough steps and timestamps to reproduce them. Verify isolation before starting the game.

## Ordered gates

1. **Full recipe baseline.** From a clean, identified source revision run the complete `build/units.json` recipe using its recorded compiler, flags and each variant. Generate one terminal result per recipe entry, including repeated sources and failed or skipped entries; reconcile the manifest against the recipe by stable entry identity, with zero missing or duplicate results and zero unexplained failures. Verify compiler versions, option and variant selection against independent recipe samples, including RTM and VC8 entries. Run the existing image fingerprint and full reference matching separately; record counts and failures without claiming a run that was not performed. A sampled build is not this gate.
2. **Retained object graph.** Privately retain an object for every successful recipe entry and map it back to that entry, configuration and object hash. Inventory defined and undefined symbols, sections, relocations, and duplicate definitions/variants. Reconcile the inventory input set and hashes against the build manifest: every retained object must have exactly one traceable inventory result, and parse errors and unsupported records must be explicit failures, not empty graphs. Check representative entries independently with a trusted COFF tool, including relocations, weak/COMDAT symbols and nonstandard records. Report all missing objects and graph edges that cannot be classified.
3. **Canonical coverage and unresolved definitions.** Independently enumerate the unique address/function obligations from the recipe, including shared addresses and all variant owners. Reconcile them with selected runtime definitions: each obligation needs a documented, evidence-backed canonical resolution or an explicit blocker; do not silently drop variants, conflate decorated names with addresses, or count duplicates as extra coverage. Record data, ABI, libraries, generated startup/runtime code, and competing definitions separately. The private link must have no unresolved external symbols and no fabricated placeholder definitions, empty stubs, hard-coded addresses, or ignored dependencies used to make it pass. A linker success is insufficient if inputs or definitions are omitted. Review a sample of selected and rejected variants against underlying evidence and explain every conflict.
4. **Startup, thread state and teardown.** Inspect entry point and initialization dependencies, CRT/static constructors, thread-local state and thread attach/detach, shutdown, static destructors and error paths. Instrument a private run to establish expected ordering and exactly-once behavior, including repeated process starts, a worker thread lifecycle, normal exit and an initialization failure path. Record known unsupported cases and crashes; no gate passes on an unexercised assertion or merely reaching `main`.
5. **Main menu.** With a verified isolated environment and owned compatible inputs, make at least two fresh launches and observe a responsive main menu; exercise navigation and normal exit. Record configuration, timings, logs, repeat steps and deviations. A window, splash screen or successful link alone is not a menu pass.
6. **New game and gameplay.** From a fresh isolated profile, start a new game and complete a predefined, repeatable route through initial gameplay, including representative movement, interaction, inventory and transition/loading behavior. Record checkpoints, observable expected state, configuration, errors and exact blockers. Expand to a documented gameplay scenario matrix covering major mechanics, transitions and stability before claiming full gameplay; a single route only establishes a smoke test. Record untested content and compatibility limits, and require all agreed scenarios to pass before claiming full coverage.
7. **Save/load.** In the isolated profile record recognizable state and location, save, exit fully, restart, load that save, and verify the same state and continued interaction. Include multiple saves, overwrite and a failed/invalid load path without touching personal saves; compare private save manifests before and after. Repeat the round trip and document any compatibility assumptions and failures. A file's existence is not proof of state integrity.
8. **Reproducibility.** On an independently prepared private environment, follow recorded setup and pinned toolchain/configuration to repeat the build, graph reconciliation and authorized smoke tests. Compare source/recipe/tool identities and output hashes where deterministic output is expected; explain nondeterminism and compare equivalent behavior where byte identity is not expected. A second run in the same configured directory is useful but is not independent reproduction.

Each gate reports PASS, FAIL, or NOT RUN with evidence and blockers. A later gate cannot retroactively pass an earlier one. Keep a separate list of assumptions and untested paths; do not call the rebuild playable, fully playable, reproducible or reference-matching until the corresponding evidence supports the specific claim.

## Negative checks for validation tooling

Use small synthetic fixtures in an isolated temporary directory, never real game code or bytes. Confirm that validation rejects a missing or duplicate recipe result, a changed recipe/object hash, an omitted variant, a failed compilation presented as success, malformed or truncated COFF data, an unsupported relocation/section record silently treated as empty, duplicate definitions without an ownership decision, and a missing address masked by a duplicate. Check that private output cannot accidentally overwrite a source input or existing artifact, and that errors produce a nonzero status and useful diagnostics. Compare at least one synthetic object against an independent COFF reader. These fixtures validate the validators; they do not establish the full-recipe or gameplay gates.
